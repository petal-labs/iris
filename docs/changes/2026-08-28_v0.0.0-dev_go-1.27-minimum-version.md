## Summary

Raises the minimum Go version from 1.24.0 to 1.27.0 across all four workspace modules, all seven
CI workflow toolchain pins, the `iris init` project scaffold, and the documented prerequisites.
Grouped dependency updates began pulling in modules that declare `go >= 1.25.0`, which a workspace
declaring `go 1.24.0` refuses to build. Go 1.27.0 is the current stable release.

## Motivation

Dependabot PRs #104 (`otel-go-modules` in `/contrib/otel`) and #105 (`root-go-modules`) failed every
build, test, lint, and security job with:

```
go: module contrib/otel listed in go.work file requires go >= 1.25.0,
    but go.work lists go 1.24.0; to update it:
	go work use
```

PR #106 (`github-actions` group) passed, which localized the fault to the Go module graph rather
than the CI runner image: the bumped OpenTelemetry modules raised their own `go` directive past what
this workspace declared. Go will not build a workspace whose `go.work` declares a lower version than
any member module requires, so the failure was total rather than partial.

The floor was moved to 1.27.0 rather than the strictly-required 1.25.0 as a deliberate project
decision to track the current stable release.

## Usage Examples

### Example: building on a machine with an older toolchain

No manual toolchain install is required. Go fetches what the module declares:

```console
$ go version
go version go1.26.7 darwin/arm64

$ go build ./... ./contrib/otel/... ./examples/...
go: downloading go1.27.0 (darwin/arm64)

$ go version
go version go1.27.0 darwin/arm64
```

### Example: error case — a consumer pinned below the new floor

A downstream module declaring less than `go 1.27.0` and depending on Iris now fails to build:

```console
$ go build ./...
go: github.com/petal-labs/iris@v0.18.0 requires go >= 1.27.0
	(running go 1.26.7; GOTOOLCHAIN=local)
```

The fix is either raising the consumer's own `go` directive to `1.27.0`, or unsetting
`GOTOOLCHAIN=local` so the required toolchain is fetched automatically.

## Integration Notes

- The four `go` directives are a single unit. Raising `go.work` alone leaves per-module builds
  (`go build` inside `contrib/otel`) still declaring the old floor; raising the modules alone leaves
  the original workspace error in place.
- The `iris init` scaffold is coupled to the SDK's own floor in a way that is easy to miss: a
  generated project declaring `go 1.24.0` cannot satisfy a dependency declaring `go 1.27.0`, and Go
  reports this as `updates to go.mod needed; to update it: go mod tidy` rather than as a version
  conflict. `TestGeneratedProjectsCompile` caught this because it runs a real `go test ./...` inside
  each of the ten scaffolded provider projects.
- `scaffoldSDKVersion` remains `v0.17.0` and was deliberately not touched here; it tracks the last
  published SDK tag, not the Go toolchain, and updating it belongs to the release process.
- Historical records under `docs/changes/` and the plan documents under `docs/superpowers/plans/`
  still reference Go 1.24. They are point-in-time records and were left as written.

## Static-Analysis Toolchain Impact

Raising the module's `go` directive past what a static-analysis tool was **built with** breaks that
tool, independently of the toolchain CI installs. Both lint jobs failed on the first attempt at this
change even though `setup-go` had correctly provisioned Go 1.27.0.

### golangci-lint

golangci-lint refuses outright when its own build version trails the target:

```
Error: can't load config: the Go language version (go1.26) used to build golangci-lint
is lower than the targeted Go version (1.27.0)
```

The pinned `v2.1.6` (released 2026-05-06) predates Go 1.27 entirely. Note that a release's `go.mod`
directive is *not* the relevant number — that is a minimum, not the toolchain the release binary was
compiled with. The authoritative check is the binary itself:

```console
$ golangci-lint version
golangci-lint has version 2.13.2 built with go1.27.0 from 27774aaf on 2026-08-27T23:01:12Z
```

`v2.13.2` is the first release built with go1.27.0, so the action pin moved `v2.1.6` → `v2.13.2`.

### gosec

The `securego/gosec` Docker action fails differently. Its image bundles its own Go and pins
`GOTOOLCHAIN=local`, so the in-container `go list` cannot fetch the required toolchain:

```
loading files from package ".": err: exit status 1: stderr:
go: go.work requires go >= 1.27.0 (running go 1.25.3; GOTOOLCHAIN=local)
```

Bumping the action does not fix this: `securego/gosec@v2.29.0`'s `action.yml` still resolves to a
`2.28.0` image built on an older `golang:*-alpine` base. The job therefore installs gosec from
source, so it compiles against the toolchain `setup-go` provisioned:

```yaml
- name: Install gosec
  run: go install github.com/securego/gosec/v2/cmd/gosec@v2.29.0

- name: Run gosec
  run: gosec -exclude=G101,G104,G301,G304,G306,G404,G703 -exclude-dir=examples -exclude-dir=contrib ./...
```

This trades a digest-pinned image for a version-pinned source build. The version remains explicitly
pinned, and the module proxy plus `go.sum` verification cover integrity.

### Newly surfaced findings

Moving golangci-lint across twelve minor versions activated gosec rules that did not exist in
`v2.1.6`. Eight findings appeared, none pre-existing failures:

| Rule | Count | Location | Disposition |
|---|---|---|---|
| G115 (integer overflow int → rune) | 3 | `core/client_test.go`, `core/retry_test.go`, `tools/registry_test.go` | Excluded for `_test.go`; test names build runes from small loop counters |
| G120 (unbounded form parsing) | 3 | `providers/anthropic/client_files_test.go`, `providers/openai/client_batch_test.go`, `providers/openai/client_files_test.go` | Excluded for `_test.go`; `httptest` handlers parse fixed-size fixture forms |
| G204 (subprocess with variable) | 1 | `cli/commands/init_test.go` | Excluded for `_test.go`; the scaffold test shells out to the Go toolchain by design |
| G703 (path traversal via taint analysis) | 1 | `cli/keystore/file.go:477` | Excluded globally, same rationale as the existing G304 exclusion |

The G703 finding is the only one in production code and was reviewed rather than blanket-excluded.
`backupPath` is `f.path + ".bak"`, where `f.path` comes from `DefaultKeystorePath()`
(`~/.iris/keys.enc`) or a location the operator passes to `NewKeystoreAtPath`. No untrusted or
remote input reaches it, the backup is written beside the user's own keystore, and the file mode is
`0600`. This is the same "CLI intentionally handles user-specified paths" case the repository
already documents for G304.

## Breaking Changes & Migration

**For SDK consumers.** The `go` directive in `go.mod` is a minimum requirement, not a preference, so
this raises the floor for everyone importing `github.com/petal-labs/iris`. Consumers on Go 1.26 or
earlier must either raise their own module's `go` directive:

```diff
-go 1.26.0
+go 1.27.0
```

or rely on the default `GOTOOLCHAIN=auto` to fetch Go 1.27.0 automatically. Only environments that
set `GOTOOLCHAIN=local` and run an older toolchain are hard-blocked.

**For contributors.** No action needed beyond a `go build`; the toolchain is fetched on demand.

**For `iris init` users.** Projects generated before this change still declare `go 1.24.0`. If such
a project is updated to an Iris version at or beyond this change, its `go.mod` needs the same bump.

## Deferred / Out of Scope

- Adding an explicit `toolchain` directive to any module.
- Updating `scaffoldSDKVersion`, which is stale at `v0.17.0` relative to the unreleased changelog.
- Rebasing or merging the Dependabot PRs (#104, #105, #106) that motivated this change.
- Fixing, rather than excluding, the newly surfaced G115/G120/G204 findings in test files.
- Restoring a digest-pinned container for gosec once an image built on Go 1.27 is published.
- Backfilling Go version references in historical `docs/changes/` and `docs/superpowers/plans/`
  records.
- Adopting any Go 1.25, 1.26, or 1.27 language or standard-library feature. This change only raises
  the floor; no source was rewritten to use newer APIs.
