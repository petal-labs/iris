## Summary

This change closes issue #44 by extending Iris's timeout handling from chat/streaming (already covered by `core.WithTimeout` as of `v0.15.0`) to every other call surface that previously had none: batch-timeout error identity, tool-execution timeout typing, streaming stall detection, and a real, enforced default timeout on every provider's non-chat unary operations (embeddings, files, images, batch, vector stores). It also un-deprecates the per-provider `WithTimeout`/`Config.Timeout` option across all nine providers, giving it real effect for the first time on eight of them. Five previously-independent gaps (identified as items 1-5 in the design doc) are addressed; each is detailed below.

## Motivation

Prior to this work, `core.WithTimeout` bounded chat/streaming calls end-to-end, but a large surface of provider methods that bypass `core.Client` — embeddings, file upload/list/get/delete, image generation/edit, batch create/status/results/cancel/list, vector store CRUD — had no Iris-imposed bound at all. A caller who forgot to pass a context deadline could hang indefinitely on a stalled HTTP request to any of these endpoints. Separately, three sharp edges made the *existing* timeout errors hard to act on: `ErrTimeout` messages didn't say which provider/model timed out (item 3), `tools.WithTimeout`'s error didn't satisfy `errors.Is(err, core.ErrTimeout)` so callers had no uniform way to detect a tool timeout (item 4), and `core.BatchWaiter.Wait` could misreport a provider's own timeout error as a generic `ErrBatchTimeout` even when the wall-clock `maxWait` budget hadn't actually elapsed (item 5). Finally, chat streaming had an overall timeout but no way to detect a stream that goes silent mid-response without actually erroring — a stalled SSE connection could sit open indefinitely under `WithTimeout(0)` or a long execution timeout (item 2). See `docs/superpowers/specs/2026-08-02-issue-44-timeout-coverage-design.md` for the full design rationale and `docs/superpowers/plans/2026-08-02-issue-44-timeout-coverage.md` for the task breakdown (Tasks 1-8).

## What Changed

### New Additions

- `core.WithStreamIdleTimeout(d time.Duration) ClientOption` (`core/client.go`) — configures a stall/idle watchdog for `ChatBuilder.Stream`. If no chunk arrives within `d`, the stream is terminated and the error delivered on `ChatStream.Err` satisfies `errors.Is(err, core.ErrTimeout)`. Independent of `WithTimeout`, which bounds total call duration; this bounds the gap between chunks. Default `0` disables idle detection (opt-in, no behavior change for existing callers).
- `core/stream_idle.go`: `wrapStreamWithIdleTimeout(stream *ChatStream, d time.Duration, cancel context.CancelFunc) *ChatStream` — internal helper implementing the watchdog goroutine. Losslessly forwards `Ch`/`Err`/`Final`, resetting the idle timer on every chunk and firing `cancel()` + `newStreamIdleError(d)` on stall.
- `core.newStreamIdleError(d time.Duration) error` (`core/errors.go`, unexported) — builds `"iris: stream idle execution timeout after %s"`, wrapping both `core.ErrTimeout` and `context.DeadlineExceeded`.
- `providers/internal/timeoutx` (new package, `providers/internal/timeoutx/timeoutx.go`):
  - `const Default = 600 * time.Second` — the default per-provider timeout applied to non-chat unary operations.
  - `func Apply(ctx context.Context, d time.Duration) (context.Context, context.CancelFunc)` — bounds `ctx` by `d` unless `d <= 0` (no-op) or `ctx` already carries a deadline (caller's deadline always wins). Returns a no-op cancel func when nothing was applied, so callers can unconditionally `defer cancel()`.
- Per-provider `Config.Timeout time.Duration` and `WithTimeout(d time.Duration) Option` un-deprecated on all nine providers (`anthropic`, `azurefoundry`, `gemini`, `huggingface`, `ollama`, `openai`, `perplexity`, `voyageai`, `xai`, `zai`) — see "Un-deprecation" below.

### Modifications

- **Item 3 — timeout errors now name the provider and model** (`core/errors.go`, `core/client.go`):
  - `newTimeoutError` signature changed from `newTimeoutError(d time.Duration) error` to `newTimeoutError(d time.Duration, provider string, model ModelID) error`. Message format changed from `"iris: execution timeout after %s: %w"` to `"iris: execution timeout after %s (provider=%s, model=%s): %w"`.
  - Both call sites in `core/client.go` (`ChatBuilder.Chat`'s retry-loop deadline mapping, and `ChatBuilder.Stream`'s immediate-error and mid-stream `mapErr` mapping) updated to pass `providerID` and `b.req.Model`.
- **Item 4 — `tools.WithTimeout` error now satisfies `core.ErrTimeout`** (`tools/middleware_timeout.go`): the timeout branch's error changed from `fmt.Errorf("tool execution timeout after %v: %w", d, context.DeadlineExceeded)` to `fmt.Errorf("tool execution timeout after %v: %w: %w", d, core.ErrTimeout, context.DeadlineExceeded)`, so `errors.Is(err, core.ErrTimeout)` now holds in addition to the pre-existing `errors.Is(err, context.DeadlineExceeded)`. Requires the new import `github.com/petal-labs/iris/core` in `tools/middleware_timeout.go`.
- **Item 5 — `core.BatchWaiter.Wait` keys `ErrBatchTimeout` on the wall-clock deadline** (`core/batch.go`): previously, any `GetBatchStatus` error alongside `errors.Is(err, context.DeadlineExceeded)` (e.g. from the per-poll `context.WithDeadline`) was reported as `core.ErrBatchTimeout`, which could mask a provider's own timeout error if the poll context happened to expire for unrelated reasons before `maxWait` truly elapsed. `Wait` now checks `!time.Now().Before(deadline)` (i.e., has the wall-clock `maxWait` budget actually run out) instead of inspecting the error chain, and returns the provider's original `err` unchanged whenever the wall-clock budget still has time left — preserving the provider's own error over a generic batch-timeout label.
- **Item 2 — stream idle timeout wiring** (`core/client.go`): `Client` gained a `streamIdleTimeout time.Duration` field. `ChatBuilder.Stream` now derives a cancellable child context (independent of, and nested inside, any execution-timeout deadline) when `streamIdleTimeout > 0`, wraps the returned `*ChatStream` with `wrapStreamWithIdleTimeout` *before* the existing telemetry wrapper (so telemetry observes the idle-wrapped channels and still fires its end-of-stream event correctly), and updated `mapErr` to leave any error that already satisfies `errors.Is(e, ErrTimeout)` (such as the idle error) unchanged instead of re-wrapping it as a generic execution-timeout error — since an idle stall does not imply the overall execution timeout has elapsed.
- **Item 1 — 600s default op-timeout on non-chat unary provider calls**: every provider's `New`/`NewWithCredential` constructor now sets `Config.Timeout: timeoutx.Default` (600s) unless overridden by `WithTimeout`. Each non-chat unary method that previously had no bound now opens with:
  ```go
  ctx, cancel := timeoutx.Apply(ctx, p.config.Timeout)
  defer cancel()
  ```
  Methods covered, by provider (all previously documented as "does not go through core.Client, so core.WithTimeout does not apply; pass a context with a deadline if a bound is needed" — that comment is now updated in-place to describe the `p.config.Timeout` bound):
  - `providers/openai`: `CreateEmbeddings`; `UploadFile`, `ListFiles`, `GetFile`, `DeleteFile`; `GenerateImage`, `EditImage`; `CreateBatch`, `GetBatchStatus`, `GetBatchResults`, `CancelBatch`, `ListBatches`; `CreateVectorStore`, `ListVectorStores`, `GetVectorStore`, `DeleteVectorStore`, `AddFileToVectorStore`, `ListVectorStoreFiles`, `GetVectorStoreFile`, `DeleteVectorStoreFile`.
  - `providers/anthropic`: `UploadFile`, `GetFile`, `ListFiles`, `ListAllFiles`, `DeleteFile`.
  - `providers/gemini`: `UploadFile`, `GetFile`, `ListFiles`, `ListAllFiles`, `DeleteFile`; `GenerateImage`, `EditImage`.
  - `providers/huggingface`: `GetModelStatus`, `GetModelProviders`, `ListModels`.
  - `providers/ollama`: `CreateEmbeddings`.
  - `providers/voyageai`: `CreateEmbeddings`, `CreateContextualizedEmbeddings`, `Rerank`.
  - `providers/azurefoundry`: `CreateEmbeddings` (refactored from an ad hoc `if p.config.Timeout > 0 { ctx, cancel = context.WithTimeout(...) }` block to `timeoutx.Apply`, which additionally now respects an existing caller deadline instead of always overriding it).
  - `providers/perplexity`, `providers/xai`, `providers/zai`: gained the default-timeout constructor wiring and the un-deprecated `WithTimeout` option, but have no non-chat unary methods today, so there is currently nothing for `timeoutx.Apply` to guard in these three packages.
  - **Explicitly excluded** (see "Deferred / Out of Scope"): reader-returning `DownloadFile` (all providers that have one), streaming `StreamImage` (none of the covered providers currently expose this as a public method, but any future one should follow the streaming exclusion, not the unary one), and poll-loop methods (`WaitForFileActive`, `PollVectorStoreUntilReady` — not present as public methods in this codebase; the exclusion is a general principle carried in code comments for any future poll helper).
- **Pre-existing bug fix uncovered by the new default** (`providers/azurefoundry/client_chat.go`): applying a real default timeout to Azure Foundry exposed a premature-cancellation bug in `doStreamChat` — the old code did `defer cancel()` inside `doStreamChat` itself, which fired as soon as the function returned, cancelling the context (and thus the SSE HTTP request) before the stream-reading goroutine (started by `processSSEStream` after `doStreamChat` returns) had a chance to read the body. Fixed by introducing `cancelOnCloseBody`, an `io.ReadCloser` wrapper that ties `cancel` to the response body's `Close()` instead of to `doStreamChat`'s return, so the timeout context now stays alive for the actual lifetime of the streamed response.

### Removals

N/A — no public API was removed. The per-provider `WithTimeout`/`Config.Timeout` deprecation notices were removed (see "Un-deprecation" and "Breaking Changes & Migration"), but the symbols themselves were retained and are now functional rather than inert.

## Technical Specification

### Go Package API

```go
// core/client.go
func WithStreamIdleTimeout(d time.Duration) ClientOption

// core/errors.go
func newTimeoutError(d time.Duration, provider string, model ModelID) error // unexported, signature changed
func newStreamIdleError(d time.Duration) error                              // unexported, new

// providers/internal/timeoutx/timeoutx.go
package timeoutx

const Default = 600 * time.Second

func Apply(ctx context.Context, d time.Duration) (context.Context, context.CancelFunc)
```

`timeoutx.Apply` contract: if `d <= 0`, returns `ctx` unchanged and a no-op cancel. If `ctx` already has a deadline (`ctx.Deadline()` returns `ok == true`), returns `ctx` unchanged and a no-op cancel — an explicit caller-supplied deadline always takes priority over the provider's configured `Timeout`. Otherwise returns `context.WithTimeout(ctx, d)`. Callers always `defer cancel()` unconditionally.

`core.WithStreamIdleTimeout` contract: `d <= 0` (including the zero value) disables idle detection entirely — no watchdog goroutine is started and `ChatBuilder.Stream` behaves exactly as before this change. When `d > 0`, the watchdog resets on every chunk delivered on `ChatStream.Ch`; if `d` elapses with no chunk, the stream's underlying provider context is cancelled and `ChatStream.Err` receives an error satisfying `errors.Is(err, core.ErrTimeout)` (and `errors.Is(err, context.DeadlineExceeded)`).

### Data Schemas / Types

```go
// core/client.go — new field on the existing Client struct
type Client struct {
    provider          Provider
    telemetry         TelemetryHook
    retry             RetryPolicy
    warningHandler    WarningHandler
    timeout           time.Duration
    streamIdleTimeout time.Duration // new
}
```

```go
// providers/azurefoundry/client_chat.go — new unexported type
type cancelOnCloseBody struct {
    io.ReadCloser
    cancel context.CancelFunc
}

func (c *cancelOnCloseBody) Close() error // closes underlying body, then calls cancel
```

### Configuration

Each provider's `Config.Timeout time.Duration` field (already existed on all nine providers) now:
- Defaults to `timeoutx.Default` (600s) when unset, applied in each provider's `New`/`NewWithCredential` constructor.
- Is honored by every non-chat unary method listed above via `timeoutx.Apply(ctx, p.config.Timeout)`.
- Can be disabled per-provider by passing `provider.WithTimeout(0)` — `timeoutx.Apply` treats `d <= 0` as "no bound applied."
- Is always overridden by an explicit context deadline passed by the caller (`timeoutx.Apply` never shortens or replaces an existing deadline).
- Does **not** affect `Chat`/`StreamChat` on any provider — those remain governed solely by `core.WithTimeout` (the `core.Client`-level option) and caller-supplied context deadlines, exactly as before this change.

## Usage Examples

### Example: detecting a stalled stream with `WithStreamIdleTimeout`

```go
client := core.NewClient(openai.New(apiKey),
    core.WithStreamIdleTimeout(30*time.Second), // no chunk for 30s -> terminate
)

stream, err := client.Chat("gpt-4o").User("Tell me a long story").Stream(context.Background())
if err != nil {
    log.Fatal(err)
}

for {
    select {
    case chunk, ok := <-stream.Ch:
        if !ok {
            continue
        }
        fmt.Print(chunk.Delta)
    case err := <-stream.Err:
        if errors.Is(err, core.ErrTimeout) {
            fmt.Println("\nstream stalled for 30s, aborting")
            return
        }
        log.Fatal(err)
    case resp := <-stream.Final:
        fmt.Println("\ndone:", resp.FinishReason)
        return
    }
}
```

### Example: raising or disabling the 600s default op-timeout on a non-chat call

```go
// Raise the default 600s bound to 20 minutes for large batch jobs.
provider := openai.New(apiKey, openai.WithTimeout(20*time.Minute))

// Or disable the Iris-imposed bound entirely and rely on the caller's
// own context deadline (or no deadline at all).
provider := openai.New(apiKey, openai.WithTimeout(0))
bp, _ := core.AsBatchProvider(provider)
batchID, err := bp.CreateBatch(context.Background(), requests) // no 600s ceiling now
```

### Example: error case — an embeddings call exceeding the new 600s default

```go
provider := ollama.New() // Config.Timeout defaults to timeoutx.Default (600s)
resp, err := provider.CreateEmbeddings(context.Background(), req)
if err != nil {
    // After this change: fails at 600s instead of hanging indefinitely.
    if errors.Is(err, context.DeadlineExceeded) {
        log.Println("embeddings call exceeded the 600s default; consider ollama.WithTimeout(...) or a longer ctx deadline")
    }
}
```

## Integration Notes

- The 600s default is intentionally generous (matched to typical large-batch/large-file operation durations) rather than tuned per-endpoint; per-method override was explicitly deferred (see below) in favor of shipping one uniform, always-on floor first.
- `timeoutx.Apply`'s "caller deadline wins" rule means existing callers who already pass a context with a deadline (however long) see zero behavior change from this release — the new default only engages when no deadline was previously set, which was previously an unbounded wait.
- The idle-stream watchdog (item 2) and the per-call op-timeout (item 1) are independent mechanisms guarding different failure modes: item 2 catches a stream that goes silent mid-response without erroring; item 1 catches any non-chat call (or the initial connection phase of a chat/stream call, via the pre-existing `core.WithTimeout`) that never completes at all. Neither subsumes the other.
- The `core.BatchWaiter` fix (item 5) only affects `Wait`'s own error classification; it does not change `GetBatchStatus`'s per-poll `context.WithDeadline` behavior, which still bounds each individual poll by the earlier of the caller's context deadline and the remaining `maxWait` budget.
- The Azure Foundry `cancelOnCloseBody` fix is defensive and provider-internal; it does not change `AzureFoundry`'s public API, only the correctness of `doStreamChat` under a now-real default timeout that previously happened to be a no-op (`Config.Timeout` defaulted to `0` before this release).

## Breaking Changes & Migration

1. **600s default op-timeout on non-chat unary calls.** Embeddings, file, image, batch, and vector-store operations across all providers that expose them now fail with a timeout error after 600 seconds by default, where previously they could hang indefinitely absent a caller-supplied context deadline. **Migration:** if an operation legitimately needs longer than 10 minutes (e.g., very large file uploads, batch polling helpers wrapping `GetBatchStatus`), either pass a context with a longer deadline, or call `provider.WithTimeout(<duration>)` (or `provider.WithTimeout(0)` to disable the Iris-imposed bound entirely and fall back to "no bound unless the context has one").
2. **Provider `WithTimeout`/`Config.Timeout` un-deprecated and now functional.** On eight providers (`anthropic`, `gemini`, `huggingface`, `ollama`, `perplexity`, `voyageai`, `xai`, `zai`) this option was previously documented as `Deprecated` and explicitly "inert — has no effect on requests." It is no longer deprecated and now has real effect (governing the new op-timeout described above). **Migration:** any caller who set `WithTimeout` on one of these eight providers expecting it to be a no-op (e.g., set defensively or copy-pasted from another provider) will now see it actually bound their non-chat unary calls. Audit any existing `WithTimeout` calls on these providers for an intended duration. `azurefoundry`'s `WithTimeout` was already functional for `doChat`/`doStreamChat` before this change and gains the same new non-chat coverage; `openai`'s `WithTimeout` was already functional as of `v0.16.0`.
3. **`core.ErrTimeout` message format changed.** `newTimeoutError`'s message changed from `"iris: execution timeout after %s: ..."` to `"iris: execution timeout after %s (provider=%s, model=%s): ..."`. `errors.Is(err, core.ErrTimeout)` and `errors.Is(err, context.DeadlineExceeded)` continue to hold unchanged — only the string form changed. **Migration:** any caller doing string-matching or substring parsing against this error's `.Error()` output (rather than `errors.Is`) must update to account for the new `(provider=..., model=...)` segment.

## Deferred / Out of Scope

- **Idle timeout for non-chat streaming methods** (e.g., a future `StreamImage`): `WithStreamIdleTimeout` (item 2) only wraps `ChatBuilder.Stream`'s `*core.ChatStream`. No provider in this codebase currently exposes a public non-chat streaming method, so this is a forward-looking exclusion, not an active gap.
- **Per-method timeout overrides.** All non-chat unary methods on a given provider share one `Config.Timeout` value; there is no way to set a shorter timeout for, say, `ListFiles` and a longer one for `CreateBatch` on the same provider instance without instantiating two provider instances with different `WithTimeout` values.
- **`DownloadFile` and other reader-returning methods.** Any method that returns an `io.ReadCloser` for the caller to stream from (e.g., `DownloadFile` on `openai`/`anthropic`/`gemini`) is intentionally excluded from `timeoutx.Apply`, since bounding the HTTP round-trip would also bound the caller's read of a body they may still be consuming well after the call returns — the same class of hazard the `azurefoundry` `cancelOnCloseBody` fix exists to prevent for streaming chat.
- **Poll-loop methods** (e.g., a hypothetical `WaitForFileActive` or `PollVectorStoreUntilReady`): not present as public methods anywhere in this codebase today, but the design intentionally carves out an exclusion for any future poll-loop helper, since a single-operation op-timeout is the wrong bound for a method whose entire purpose is to wait across many polls (that class of method should use its own `maxWait`/`pollInterval` pattern, as `core.BatchWaiter` already does).
