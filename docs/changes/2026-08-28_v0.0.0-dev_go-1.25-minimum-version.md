## Summary

Raises the minimum Go version from 1.24.0 to 1.25.0 across all four workspace modules, all seven
CI workflow toolchain pins, the `iris init` project scaffold, and the documented prerequisites, and
moves the pinned golangci-lint from `v2.1.6` to `v2.5.0` so the linter can analyze the raised target.
Grouped dependency updates began requiring `go >= 1.25.0`, which a workspace declaring `go 1.24.0`
refuses to build.

## Motivation

Dependabot PRs #104 (`otel-go-modules` in `/contrib/otel`) and #105 (`root-go-modules`) failed every
build, test, lint, and security job with:

```
go: module contrib/otel listed in go.work file requires go >= 1.25.0,
    but go.work lists go 1.24.0; to update it:
	go work use
```

PR #106 (`github-actions` group) passed, which localized the fault to the Go module graph rather
than the CI runner image: the bumped OpenTelemetry modules raised their own `go` directive past what
this workspace declared. Go will not build a workspace whose `go.work` declares a lower version than
any member module requires, so the failure was total rather than partial.

`1.25.0` is the exact version the dependency graph demands. It was chosen over a newer release
deliberately — see **Version Selection** below.

## Version Selection

The floor was set to the minimum the dependencies actually require rather than to the newest stable
release (`1.27.0` at time of writing). Static-analysis tools are constrained by the Go version they
were **built with**, not the version CI installs, and that ecosystem trails a Go release by weeks:

| Floor | golangci-lint | gosec Docker action | Net cost |
|---|---|---|---|
| `1.25.0` | `v2.5.0` (built `go1.25.1`) works, 0 findings | image ships `go1.25.3` — works as-is | linter pin bump only |
| `1.26.0` | `v2.13.2` needed | image `go1.25.3` **too old** — action must be replaced | linter bump + CI restructure |
| `1.27.0` | only `v2.13.2` (built `go1.27.0`, released 2026-08-27) | image `go1.25.3` **too old** — action must be replaced | linter bump + CI restructure + 8 new findings to triage |

At `1.25.0` the digest-pinned `securego/gosec` action keeps working unchanged, and no new lint
exclusions are needed. Raising the floor further can be revisited once the tool ecosystem catches up.

Note that a linter bump is unavoidable at *any* floor above 1.24: the pinned `v2.1.6` is
`built with go1.24.2` and refuses a higher target. That cost is not specific to the floor chosen.

## Usage Examples

### Example: building on a machine with an older toolchain

No manual toolchain install is required. Go fetches what the module declares:

```console
$ go version
go version go1.24.2 darwin/arm64

$ go build ./... ./contrib/otel/... ./examples/...
go: downloading go1.25.3 (darwin/arm64)
```

### Example: error case — a consumer pinned below the new floor

A downstream module declaring less than `go 1.25.0` and depending on Iris now fails to build:

```console
$ go build ./...
go: github.com/petal-labs/iris@v0.18.0 requires go >= 1.25.0
	(running go 1.24.2; GOTOOLCHAIN=local)
```

The fix is either raising the consumer's own `go` directive to `1.25.0`, or unsetting
`GOTOOLCHAIN=local` so the required toolchain is fetched automatically.

## Static-Analysis Toolchain Impact

Raising the module's `go` directive past what a static-analysis tool was **built with** breaks that
tool, independently of the toolchain CI installs. golangci-lint refuses outright:

```
Error: can't load config: the Go language version (go1.24) used to build golangci-lint
is lower than the targeted Go version (1.25.0)
```

The pinned `v2.1.6` reports `built with go1.24.2` (released 2025-05-04), so it cannot analyze a
`go 1.25.0` module. Note that a release's `go.mod` directive is *not* the relevant number — that is
a minimum, not the toolchain the release binary was compiled with. The authoritative check is the
binary itself:

```console
$ golangci-lint version
golangci-lint has version 2.5.0 built with go1.25.1 from ff63786c on 2025-09-21T19:04:05Z
```

`v2.5.0` is built with `go1.25.1` and produces **0 findings** against the unchanged `.golangci.yml`,
so no lint exclusions were added. `v2.4.0` (`built with go1.25.0`) also works and was verified; the
slightly newer `v2.5.0` was chosen as the pin.

`gosec` needs no change at this floor. The `securego/gosec` Docker action bundles its own Go and
pins `GOTOOLCHAIN=local`, so it can only load modules at or below the image's Go version — that
image ships `go1.25.3`, which satisfies a `go 1.25.0` target. The action keeps its existing commit
pin, image digest, and exclude list.

## Integration Notes

- The four `go` directives are a single unit. Raising `go.work` alone leaves per-module builds
  (`go build` inside `contrib/otel`) still declaring the old floor; raising the modules alone leaves
  the original workspace error in place.
- The `iris init` scaffold is coupled to the SDK's own floor in a way that is easy to miss: a
  generated project declaring `go 1.24.0` cannot satisfy a dependency declaring `go 1.25.0`, and Go
  reports this as `updates to go.mod needed; to update it: go mod tidy` rather than as a version
  conflict. `TestGeneratedProjectsCompile` caught this because it runs a real `go test ./...` inside
  each of the ten scaffolded provider projects.
- Local verification must use a matching toolchain. A golangci-lint built with `go1.25.x` panics
  while reading export data produced by a `go1.26`/`go1.27` toolchain, even when the module targets
  `1.25.0`. Reproduce CI faithfully with `GOTOOLCHAIN=go1.25.3`; the panic is an artifact of the
  local toolchain, not a code defect.
- `scaffoldSDKVersion` remains `v0.17.0` and was deliberately not touched here; it tracks the last
  published SDK tag, not the Go toolchain, and updating it belongs to the release process.
- Historical records under `docs/changes/` and the plan documents under `docs/superpowers/plans/`
  still reference Go 1.24. They are point-in-time records and were left as written.

## Breaking Changes & Migration

**For SDK consumers.** The `go` directive in `go.mod` is a minimum requirement, not a preference, so
this raises the floor for everyone importing `github.com/petal-labs/iris`. Consumers on Go 1.24 must
either raise their own module's `go` directive:

```diff
-go 1.24.0
+go 1.25.0
```

or rely on the default `GOTOOLCHAIN=auto` to fetch Go 1.25 automatically. Only environments that
set `GOTOOLCHAIN=local` and run an older toolchain are hard-blocked.

**For contributors.** No action needed beyond a `go build`; the toolchain is fetched on demand.
Contributors running golangci-lint locally need `v2.5.0` or newer.

**For `iris init` users.** Projects generated before this change still declare `go 1.24.0`. If such
a project is updated to an Iris version at or beyond this change, its `go.mod` needs the same bump.

## Deferred / Out of Scope

- Raising the floor to Go 1.26 or 1.27. Both require replacing the `securego/gosec` Docker action,
  because no published gosec image yet ships a Go newer than `1.25.3`, and 1.27 additionally
  requires golangci-lint `v2.13.2`, which surfaces eight previously-unreported gosec findings
  (3×G115, 3×G120, 1×G204, 1×G703) needing triage.
- Adding an explicit `toolchain` directive to any module.
- Updating `scaffoldSDKVersion`, which is stale at `v0.17.0` relative to the unreleased changelog.
- Rebasing or merging the Dependabot PRs (#104, #105, #106) that motivated this change.
- Backfilling Go version references in historical `docs/changes/` and `docs/superpowers/plans/`
  records.
- Adopting any Go 1.25 language or standard-library feature. This change only raises the floor; no
  source was rewritten to use newer APIs.
