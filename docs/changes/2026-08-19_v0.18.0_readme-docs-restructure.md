## Summary

The root `README.md` was reduced from 1,241 lines to 297 by relocating its
reference-length material into topic pages under `docs/`. A new `docs/README.md`
serves as the documentation index. Ten task-focused guides were created under
`docs/guides/`, a `docs/DEVELOPMENT.md` was created from the README's project
structure and development sections, and the README's provider status table plus
model catalogs were merged into the existing `docs/PROVIDERS.md`. No SDK, CLI, or
schema behavior changed. One test helper was scoped more precisely (see
Testing Notes) — no runtime code was modified.

## Motivation

The README had accumulated every SDK feature walkthrough, the full model catalog
for five providers, and the entire contributor development guide. A reader
looking for "how do I make one chat call" had to scroll past roughly 1,100 lines
of reference material, and the model tables had drifted out of sync with the
per-provider tables already maintained in `docs/PROVIDERS.md`.

The README now answers exactly one question — how to install Iris and make a
first call, from the SDK or the CLI — and links out for everything else.

### Example: verifying a model table against code

The provider model catalogs in `docs/PROVIDERS.md` mirror each provider's
`Models()` method. To regenerate the underlying data:

```go
package main

import (
    "fmt"
    "strings"

    "github.com/petal-labs/iris/core"
    "github.com/petal-labs/iris/providers/xai"
)

func main() {
    for _, m := range xai.New("unused").Models() {
        caps := make([]string, 0, len(m.Capabilities))
        for _, c := range m.Capabilities {
            caps = append(caps, string(c))
        }
        fmt.Printf("| %s | %s | %s |\n", m.ID, m.DisplayName, strings.Join(caps, ", "))
    }
}
```

Constructing a provider with a placeholder key is safe here: `Models()` returns
a static catalog and makes no network call.

## Testing Notes

### Test change

Adding the `## Supported Providers` status table to `docs/PROVIDERS.md` broke
`TestProvidersDocMatrixAccuracy` in `tests/docs_test.go`.

That test verifies the Feature Support Matrix against each provider's
`Supports()` implementation. It located matrix rows by scanning the **entire
file** with `^\| ([^|\n]+) \|((?:[^|\n]+\|)+)$` and keeping the last row whose
first cell matched a known provider display name. The new status table shares
five of those names (`OpenAI`, `Anthropic`, `Ollama`, `Perplexity`,
`Azure AI Foundry`), so its three-column rows overrode the eleven-column matrix
rows, and every feature-cell lookup then indexed past the end of the row.

The fix adds `featureMatrixSection(t, content)`, which slices the content from
`## Feature Support Matrix` to the next `## ` heading. Row and header parsing now
read from that slice instead of the whole file. This is the table the test's own
doc comment says it checks.

This was a latent defect rather than one introduced here: any future table in
`PROVIDERS.md` keyed on provider display names would have silently overridden the
matrix rows. `matrixHeader` had the same whole-file scan but happened to survive
because it takes the first match and the matrix appears first.

The assertion was not weakened. Verified by mutation:

| Mutation | Result |
|---|---|
| Flip `Anthropic` / `Chat` from `Yes` to `No` | fails: `matrix cell Anthropic/Chat = "No", want "Yes" (Supports(chat) = true)` |
| Delete the entire `Ollama` matrix row | fails: `matrix has 9 provider rows, want 10 (missing providers: [Ollama])` |
| Unmodified | passes |
